# 회고: 인증 만료 시 로그인 ↔ 홈 무한 왕복 및 화면 깜빡임

> 2026-10-21 | 하이브리드 앱(React SPA + 네이티브 WebView) 빌딩 관리 서비스

---

## 한 줄 요약

만료된 토큰으로 앱에 진입하면 로그인과 홈 사이를 0.9초간 약 330회 왕복하며 화면이 깜빡이는 버그를, **4개 파일에 각 1줄씩 총 4줄 수정**으로 해결했다.

---

## 1. 무엇이 일어났는가

사용자가 앱을 열었을 때 "인증이 만료되었습니다" 팝업이 뜨면서 뒤 화면이 심하게 깜빡이는 현상이 보고되었다. 확인해보니 **로그인 화면과 홈 화면이 초당 수백 회 전환**되고 있었고, 전체 새로고침이 도착해야 비로소 멈추는 구조였다.

- 네트워크가 느린 환경일수록 새로고침이 늦게 도착해 깜빡임이 길어진다
- 만료 팝업은 라우트 바깥(`App`)에 있어서 왕복 중에도 떠 있다 — 팝업 뒤로 화면이 격렬하게 깜빡이는 모습

---

## 2. 발생 조건

localStorage에 `jwtToken`이 남아 있지만 서버에서는 이미 무효인 상태에서 앱을 시작할 때 발생한다.

이 상태가 만들어지는 경로:

- **Android 백업 복원**: `allowBackup="true"` + 백업 제외 규칙 없음 → 재설치/기기 이동 시 웹뷰 localStorage가 그대로 복원되어 이미 무효화된 토큰이 살아남
- **서버 측 refresh token 무효화**: 서버가 토큰을 폐기했는데 클라이언트 localStorage에는 남아있는 경우

> 앱 네이티브 코드가 토큰을 웹뷰에 주입하지 않으며, 토큰은 웹(localStorage)에만 존재한다.

---

## 3. 재현

로컬 환경에서 무효 토큰을 초기화 스크립트로 주입하고, Fast 3G 네트워크 제한 상태에서 홈 경로로 콜드 부팅하여 재현했다.

| 측정 항목 | 값 |
|----------|-----|
| 화면 전환(replaceState) 횟수 | 약 330회 |
| 왕복이 이어진 시간 | 약 0.9초 |
| 왕복을 끝낸 전체 새로고침 | 1회 |

```
replaceState /auth/login   ← 토큰 삭제 이벤트로 로그인 화면 이동
replaceState /home         ← 로그인 화면이 홈으로 보냄
replaceState /auth/login   ← 라우트 가드가 로그인으로 되돌림
replaceState /home
... (같은 패턴 약 330회 반복)
pagehide                   ← logout의 전체 새로고침 도착, 왕복 종료
```

데스크톱(네트워크 제한 없음)에서는 새로고침이 빨리 도착해 1~2회로 끝나지만, 실기기에서는 문서를 받아오는 시간만큼 왕복이 이어진다.

---

## 4. 원인 분석

### 원인 1: 로그인 화면이 토큰 존재를 확인하지 않고 홈으로 보냄 — 왕복의 직접 원인

```tsx
// 로그인 화면의 [user] effect
useEffect(() => {
  // 문제: isLoading === false만 확인, jwtToken 존재 여부는 미확인
  if (user && user.isLoading === false) {
    afterLoginNavigate();   // → 홈으로 이동
  }
}, [user]);
```

회원정보 로딩이 끝났다(`isLoading === false`)는 이유만으로 로그인 성공으로 판단하고 홈으로 보냈다. 홈에서는 라우트 가드가 토큰이 없다며 로그인으로 되돌린다. 로그인 화면이 다시 마운트되면 이 effect가 또 돌아서 **무한 왕복**이 된다.

### 원인 2: 401 응답이어도 isLoading: false가 세팅됨 — 원인 1의 트리거

```tsx
// 회원정보 조회 훅
} catch (e) {
  if (e?.response?.status === 401) {
    logout();         // await 없이 다음 줄로 진행
  }
}
// ... 함수가 끝까지 진행
await updateField({ isLoading: false });  // 실패했는데 로딩 완료 처리
```

401 catch 후 `return`이 없어서 함수가 끝까지 진행되고 `isLoading: false`가 세팅된다. 이것이 원인 1의 effect를 트리거해 홈으로 보낸다.

### 원인 3: 인증 만료 처리 경로가 세 갈래로 경합 — 왕복이 없어도 최소 1회 깜빡임

| 경로 | 동작 |
|------|------|
| 토큰 삭제 이벤트 | `tokenRemove` 커스텀 이벤트 → SPA 내에서 로그인 화면으로 navigate |
| 만료 팝업 | `setAuthExpired(true)` → 모달 표시, 확인 버튼 누르면 전체 새로고침 |
| 로그아웃 함수 | `window.location.href = "/auth/login"` 전체 새로고침 |

세 가지가 동시에 실행되면서 서로 경합한다. 원인 1·2를 고쳐도 `홈 → 로그인 + 팝업 → 빈 화면(새로고침) → 로그인` 순서의 깜빡임이 남는다.

### 원인 흐름도

```
무효 토큰으로 홈 진입
  → API 401 → 재발급 실패
  ├→ jwtToken 삭제 → tokenRemove 이벤트 → 로그인 화면 이동 + 만료 팝업
  └→ 회원정보 훅: logout() 호출(새로고침 예약) + isLoading: false 세팅
       → 로그인 화면: isLoading false 감지 → 홈으로 이동
       → 라우트 가드: 토큰 없음 → 로그인으로 이동
       → (무한 반복 ... 새로고침 도착 시 종료)
```

---

## 5. 기존 분석과의 차이

같은 증상에 대한 별도 분석이 있었다. 증상과 발생 조건은 일치했지만, 코드를 따라가본 반복 원리는 달랐다.

| 기존 분석의 주장 | 실제 코드 동작 | 판정 |
|-----------------|---------------|------|
| 401마다 만료 콜백이 N번 실행 → 새로고침 반복 | 만료 콜백은 state setter라 여러 번 불려도 팝업은 한 번만 뜸. 새로고침은 버튼 클릭 시에만 발생 | 코드와 다름 |
| logout의 signOut이 또 401을 유발 → 재귀 | 토큰이 있을 때만 signOut 호출 + `isLoggingOut` 플래그로 이중 실행 방지 | 코드와 다름 |
| 처리 안 된 401이 새로고침을 반복 | 새로고침 시 이전 요청 모두 소멸. 토큰도 없어 401 재발 불가 | 코드와 다름 |
| 토큰 삭제 이벤트와 전체 새로고침의 경합 | 동일 (위 원인 3과 같은 내용) | **일치** |

**교훈**: 증상이 같아도 원인 분석은 반드시 코드를 따라가며 검증해야 한다. 추측 기반 분석에서 수정안을 도출하면 실제 원인을 놓칠 수 있다.

---

## 6. 어떻게 해결했는가

4개 파일에 각 1줄씩, 총 4줄 변경.

### 수정 1: 로그인 화면 — 토큰 확인 추가

```diff
  useEffect(() => {
+   if (!getLocalValue("jwtToken")) return;
    if (user && user.isLoading === false) {
```

토큰이 없으면 effect를 즉시 빠져나간다. **무한 왕복의 직접 원인 차단.**

### 수정 2: 회원정보 훅 — 401 catch 후 즉시 return

```diff
  if (e?.response?.status === 401) {
    logout();
+   return;
  }
```

401이면 logout 후 즉시 종료. `isLoading: false`에 도달하지 않아 **왕복 트리거 제거.**

### 수정 3: HTTP 인터셉터 — isLoggingOut 즉시 설정

```diff
  if (error?.response?.status === 401 && !isLoggingOut) {
+   isLoggingOut = true;
    removeLocalValue("jwtToken");
```

토큰 삭제 전에 로그아웃 상태를 먼저 표시. tokenRemove 이벤트의 SPA navigate와 logout의 full reload **경합 방지.**

### 수정 4: 만료 팝업 — 확인 클릭 시 상태 리셋

```diff
  onClick={() => {
+   setAuthExpired(false);
    window.location.href = "/auth/login";
  }}
```

전체 새로고침 전에 팝업을 먼저 닫아 **새로고침 중 팝업이 남아있는 깜빡임 제거.**

### 수정 후 동작 흐름

```
무효 토큰으로 앱 진입
  → API 401 → 재발급 실패
  → isLoggingOut = true (경합 방지)
  → jwtToken 삭제 → 만료 팝업 표시
  → 회원정보 훅: 401 catch → logout() → return (isLoading: false 도달 안 함)
  → 로그인 화면: jwtToken 없음 → effect 즉시 return (홈 이동 안 함)
  → 사용자가 팝업 확인 → 팝업 닫힘 → 로그인 페이지로 이동
```

왕복 없이 만료 팝업 → 로그인 화면으로 깔끔하게 전환된다.

## 7. 남은 과제

| 항목 | 상태 | 설명 |
|------|------|------|
| Android 백업 제외 규칙 | 미적용 | `backup_rules.xml`에서 웹뷰 저장소를 제외하면 무효 토큰 복원 자체를 막을 수 있음. 앱 배포 필요 |
| 만료 처리 경로 통일 | 미적용 | 현재 3가지 경로(SPA navigate, 팝업, full reload)가 공존. 한 가지로 통일하면 코드가 단순해짐 |

---

## 8. 돌아보며

### 잘한 것

- **재현 환경을 정밀하게 구성했다.** 초기화 스크립트로 무효 토큰을 주입하고 `history` API 호출을 기록하여 왕복 횟수(~330회)와 시간(0.9초)을 정량적으로 측정할 수 있었다.
- **기존 분석을 코드 기반으로 검증했다.** 증상은 같지만 원인이 달랐던 기존 분석의 수정안이 실제로 효과가 없었을 것을 확인하고, 진짜 원인에 집중할 수 있었다.
- **최소한의 변경으로 해결했다.** 4줄 수정으로 끝냈고, 기존 로직의 구조를 바꾸지 않아 사이드 이펙트 위험이 낮았다.

### 배운 것

- **"로딩 완료"와 "성공"은 다르다.** `isLoading: false`를 성공으로 간주하는 코드는 실패 케이스에서 의도하지 않은 동작을 유발한다. 에러 상태와 로딩 상태를 분리해서 관리해야 한다.
- **비동기 처리에서 early return은 중요하다.** catch 블록에서 `return` 한 줄이 없어서 함수가 끝까지 흘러간 것이 왕복의 트리거였다. 에러 핸들링 후 함수가 어디까지 진행되는지 항상 확인해야 한다.
- **같은 이벤트에 대한 처리가 여러 곳에 분산되면 경합이 생긴다.** 인증 만료라는 하나의 이벤트를 SPA navigate, 모달, full reload 세 곳에서 각각 처리하면서 경합이 발생했다. 이상적으로는 하나의 경로로 통일하는 것이 맞다.
- **증상이 같다고 원인이 같은 것은 아니다.** 기존 분석은 합리적인 추론이었지만 코드를 따라가보면 실제 동작과 달랐다. 분석은 반드시 코드 실행 경로를 따라 검증해야 한다.
