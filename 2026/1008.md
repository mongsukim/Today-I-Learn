# **실 모니터링 청소 시작 미반영 이슈

2026-10-08 ·

청소 시작 API는 200을 받지만, 서버가 1초 안에 해당 tag의 value를 0으로 갱신해 '청소중'으로 바뀌지 않는다. 앱과 웹 모두 재현되며 프론트 문제는 아니고 서버·IoT 쪽 확인이 필요하다.

## 현상

매니저 **실 모니터링 화면(Manager******MonitoringV2)에서 '청소 시작'을 누르면 성공 토스트가 뜨고 3초 뒤 재조회하지만, 카드가 '청소중'으로 바뀌지 않고 상세의 버튼도 '청소 시작' 그대로 남는다.

- **간헐적이다:** 같은 화면의 청소 시작으로 '청소중'이 된 적도 있다.
- **청소 종료는 정상처럼 보인다:** 종료의 목표 값이 0이라, 0으로 덮어쓰는 동작이 있어도 결과가 같아 구분되지 않는다.
- **환경:** dev (app.devsni.com → api-v2.devsni.com), iOS 앱·Android 앱·PC 웹 모두 재현.
- **화면 판정 기준:** `clean[0].value === 2`일 때만 '청소중'과 '청소 종료' 버튼을 표시한다.

## 재현 증거

세 건 모두 PUT 200 이후 1초 안에 `updatedAt`이 갱신됐지만 `value`는 0이었다. (iOS 앱, Safari 웹 인스펙터로 캡처, 시각은 KST)

| **실 | tagId | 청소 시작 PUT | updatedAt | 재조회 GET | value |
| --- | --- | --- | --- | --- | --- |
| 10F 여자**실 (TR_0000108) | TAG_S01_00057013 | 15:35:41, 200 | 15:35:42 | 약 15:35:44 | 0 |
| 10F 여자**실 (TR_0000108) | TAG_S01_00057013 | 약 15:22:14 (추정) | 15:22:15 | 15:22:18 | 0 |
| 10F 남자**실 (TR_0000109) | TAG_S01_00057004 | 15:18:58, 200 | 15:18:59 | 약 15:19:02 | 0 |

- PUT: `/api/v2/app/iot/monitoring/toilet/cleaning?tagId=…&cleaningYn=true`, 응답 본문 없음(Content-Length 0).
- GET: `/api/v2/app/iot/monitoring/toilet?buildingId=BD_0000179`, 네트워크에서 수신(캐시 아님).
- 응답 헤더: `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`.
- PC 웹에서 같은 동작을 했을 때도 `value`가 0으로 왔다.

## 배제된 원인

클라이언트는 정상 요청을 보내고 서버의 최신 값을 그대로 그리고 있어, 앱·웹·React Query 쪽 원인은 없다.

| 가설 | 확인 내용 | 결과 |
| --- | --- | --- |
| React Query가 앱에서 다르게 동작 | `refetchOnWindowFocus: false`, 화면 코드에 앱 전용 분기 없음. 재조회 GET이 실제로 발생 | 배제 |
| 웹뷰 HTTP 캐시 | Android `LOAD_NO_CACHE` + `clearCache(true)`. iOS GET은 48.73KB 네트워크 수신, 서버가 no-store 응답 | 배제 |
| 앱과 웹의 서버·배포본 차이 | 앱(Sandi Dev)도 app.devsni.com → api-v2.devsni.com, 웹과 동일 | 배제 |
| 잘못된 요청 파라미터 | PUT 쿼리 `tagId`, `cleaningYn=true` 정확, 200 응답 | 배제 |
| 앱 전용 문제 | PC 웹에서도 value 0으로 재현 | 배제 |

## 추정 원인

PUT으로 value 2를 쓴 직후, 다른 경로가 같은 tag에 0을 쓰는 경쟁 상태로 추정한다. 어느 쪽이 나중에 써지느냐에 따라 성공·실패가 갈려 간헐적으로 보인다.

1. 클라이언트가 청소 시작 PUT 전송 → 서버가 value 2 기록
2. 1초 이내에 다른 경로가 value 0 기록 (`updatedAt` 갱신)
3. 3초 뒤 재조회 GET → value 0 → 화면은 '청소 시작' 유지

0을 쓰는 주체 후보:

- **센서(미화작업버튼) 상태 보고:** 실물 버튼이 눌리지 않았으므로 기기가 자기 상태 0을 보고하며 덮어씀. tag 이름이 '…_미화작업버튼_센서상태'이고 macAddr이 붙어 있어 실기기 연동 값이다.
- **서버 내부 비동기 처리:** 청소 시작 처리 중 메시지 수신·후처리 로직이 이전 상태(0)로 다시 기록.

## 영상 분석

직전 청소가 막 끝난 **실은 청소 시작이 실패하고, 마지막 청소 후 오래 지난 **실은 성공했다.   
PC 웹(크롬 모바일 에뮬레이션, BD_0000179) 화면 녹화 73초 분량을 분석했다. 시각은 응답 헤더 Date 기준 KST다.

| 영상 시점 | **실 | 동작 | 직전 상태 | 결과 |
| --- | --- | --- | --- | --- |
| 46\~53초 | 10F 남자 | 청소 시작 | 마지막 청소 후 0분 | PUT 200 (15:59:26), updatedAt 15:59:27, value 0 → 실패 |
| 40\~43초 | 10F 여자 | 청소 종료 | 청소중 | 정상 종료 |
| 32\~38초 | 10F 여자 | 청소 시작 | 마지막 청소 후 23분 | PUT 200 → '청소중' 표시 → 성공 |
| 7\~12초 | 10F 남자 | 청소 시작 | 마지막 청소 후 0분 | PUT 200 (15:58:46), 재조회 value 0 → 실패 |
| 0\~5초 | 10F 남자 | 청소 종료 | 화면은 '청소중' | PUT `cleaningYn=false` → 422 "이미 청소가 종료되었어요", 재조회 시 이미 여유 |

- **종료 직후 시작은 실패:** 같은 남자**실에서 두 번 모두 실패, 23분 비어 있던 여자**실은 성공. 종료 후 일정 시간 시작 명령을 무시하는 동작(쿨다운)이 의심된다.
- **'청소중'이 저절로 풀린 흔적:** 화면은 '청소중'이었는데 종료 요청에 서버가 '이미 종료됨'(422)으로 응답했다. 0으로 되돌아가는 동작이 PUT 직후 1초 안에만 있는 것은 아닐 수 있다.
- **실패한 시작은 청소 횟수에 미반영:** 남자**실 `todayCount`가 실패 후에도 30 그대로다.
- **앱 빈도가 높았던 이유(추정):** 앱 테스트에서 같은 **실의 종료 → 시작을 빠르게 반복해 이 조건에 더 자주 걸렸을 가능성이 높다. 캐시·쿠키와는 무관하다.
- **확정 방법:** 같은 **실에서 종료 후 10초·30초·1분·3분 간격으로 시작해 보고, 몇 초부터 성공하는지 확인한다.

## 점검할 사항

백엔드·IoT 담당이 해당 tag의 쓰기 이력을 시간순으로 보면 원인이 바로 갈린다.

- [ ] 15:18:58\~15:19:00 `TAG_S01_00057004`, 15:22:13\~15:22:16 및 15:35:40\~15:35:43 `TAG_S01_00057013`의 value 쓰기 이력 확인 (값·시각·쓴 주체)
- [ ] PUT `cleaningYn=true` 처리 시 실제로 value 2를 기록하는지 확인
- [ ] 센서(미화작업버튼) 상태 보고가 API로 쓴 값을 덮어쓰는지, 보고 주기 확인
- [ ] 청소 시작 처리의 비동기 경로(메시지 수신·후처리)에서 0을 쓰는 곳이 있는지 확인
- [ ] 청소 종료(`cleaningYn=false`)도 같은 덮어쓰기가 있는지 확인 (결과가 0이라 화면으로는 구분 불가)
- [ ] 청소중 판정 기준이 여전히 `value === 2`인지 확인 (바뀌었다면 프론트 수정 필요)

프론트에서 재조회를 늦추는 우회는 하지 않는다. 덮어쓰기라면 늦게 조회해도 0이 오기 때문이다.
