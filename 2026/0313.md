# React Query — staleTime vs gcTime 동작 정리

## Q. 전역 설정은 캐싱 시간이 항상 0이라는 거야?

네, 하지만 정확히는 **"stale 판정 시간이 0"** 입니다.

- `staleTime: 0` → 데이터를 가져오는 즉시 stale로 간주
- stale이 되면 다음 번 쿼리 사용 시 백그라운드에서 refetch 발생

즉 캐시에 데이터가 없어지는 게 아니라, 컴포넌트가 마운트되거나 윈도우 포커스가 돌아올 때마다 자동으로 재요청이 발생합니다.

`gcTime`(기본 5분)이 지나야 캐시에서 실제로 제거됩니다.

### staleTime vs gcTime 역할 비교

| 설정 | 역할 |
|------|------|
| `staleTime` | 이 시간이 지나면 "오래된 데이터"로 판정 → refetch 트리거 |
| `gcTime` | 캐시에서 실제로 데이터를 삭제하는 시간 |

> 전역 `staleTime: 0`은 "항상 최신 데이터를 보장"하는 보수적인 설정이고,
> `useBoardingRequests`처럼 5분을 명시한 쿼리는 그 시간 동안 refetch 없이 캐시 데이터를 그대로 씁니다.

---

## Q. 전역 설정은 캐싱 시간(gcTime)이 몇 분으로 되어 있어?

전역 `gcTime: 0`입니다. 컴포넌트가 언마운트되는 즉시 캐시에서 데이터가 제거됩니다.

### 전역 기본값

- `staleTime: 0` → 항상 stale
- `gcTime: 0` → 언마운트 즉시 캐시 삭제

그런데 `useBoardingRequests`는 `staleTime: 5분`, `gcTime: 5분`을 명시했기 때문에,
전역 설정을 완전히 무시하고 5분간 캐시를 유지합니다. **이게 stale 데이터 문제의 원인입니다.**

---

## Q. "컴포넌트가 언마운트된다"는 게 앱 종료 or 백그라운드 전환을 말하는 거야?

아니요, 그것보다 **더 자주** 발생합니다.

**언마운트 = 해당 컴포넌트가 화면에서 사라질 때**

예를 들어 이 앱 기준으로:

- `RouteStationDetailPage`에서 뒤로가기 → 언마운트
- 다른 탭/페이지로 라우터 이동 → 이전 페이지 언마운트

`gcTime: 0`이면 페이지를 벗어나는 순간 캐시가 삭제되고, 다시 돌아오면 새로 요청합니다.

### useBoardingRequests에 gcTime: 5분이 설정된 경우 흐름

1. `RouteStationDetailPage` 진입 → 데이터 fetch
2. 뒤로가기로 나감 → 언마운트되어도 캐시 5분 유지
3. 5분 안에 다시 진입 → 캐시 데이터 그대로 사용 (refetch 없음)

**이게 stale 데이터 문제로 이어질 수 있는 구조입니다.**

## Q. 앱 완전 종료 후 재실행 / 백그라운드 → 포그라운드 복귀 시 캐싱은 어떻게 처리돼?

### 앱 완전 종료 후 재실행

React Query 캐시는 **메모리에만 존재**합니다.
앱을 완전히 종료하면 메모리가 초기화되므로 캐시도 사라집니다.
재실행 시 항상 새로 fetch합니다.

### 앱 백그라운드 → 포그라운드 복귀

전역 설정에 `refetchOnWindowFocus: false`가 설정되어 있어,
백그라운드 복귀 시 **자동 refetch가 비활성화**되어 있습니다.
즉 메모리에 캐시가 살아있으면 그대로 사용합니다.

`useBoardingRequests`는 `gcTime: 5분`이므로, 백그라운드로 간 지 5분이 안 됐다면
캐시가 살아있고 자동 refetch도 없으니 **stale 데이터를 그대로 보여줄 수 있습니다.**

> 이게 BOARD-001 문제의 실질적인 시나리오 중 하나입니다.
