# 같은 증상, 정반대의 해결책 — iOS와 Android의 결제 복귀 트러블슈팅 회고

## 개요

외부 결제 앱(간편결제 앱 등)에서 결제를 완료한 뒤 우리 앱으로 돌아왔을 때, 정상적으로 "예약 완료" 페이지가 표시되지 않는 문제가 iOS와 Android 양쪽에서 발생했다. 같은 증상처럼 보였지만 원인은 플랫폼마다 달랐고, 결국 해결 방향도 정반대가 되었다.

### 결제 흐름 (정상 시나리오)

```
앱(WebView) → 자체 결제 모듈 → 외부 결제 앱 → 결제 완료
→ 결제 모듈이 successReturnURL로 리다이렉트
→ /reservations/success/index.html (정적 페이지)
→ SPA /reservation/complete/{id}/ (예약 완료 화면)
```

핵심은 "외부 결제 앱에서 돌아온 직후 WebView가 어떤 상태인가"였다.

## iOS 이슈

### 증상

결제 앱에서 우리 앱으로 복귀하면, 예약 완료 페이지가 아니라 **홈 화면이나 로그인 페이지**로 튕기는 현상이 발생했다.

### 원인

`CustomBridgeViewController.swift`의 `checkWebViewAndRecover()` 메서드가 **포그라운드 복귀 시** WebView 상태를 체크해서 "앱이 초기화되어 있는지"를 판단하고 있었다. 문제는 결제 모듈이나 PG 페이지에 머무른 상태에서 앱으로 복귀하는 경우였다.

1. 복귀 시점에 WebView의 현재 URL은 앱 자체 도메인(예: `app.example.com`)이 아니라 **외부 결제 도메인**(자체 결제 모듈 도메인, 외부 PG 도메인 등)이다.
2. `checkWebViewAndRecover()`가 이 상태에서 초기화 플래그(`window.appInitialized`)를 평가하면, 결제 모듈 페이지에는 해당 변수가 없으므로 `false`를 반환한다.
3. 앱이 초기화되지 않은 것으로 오판하여 앱을 루트로 리로드하는 복구 로직을 호출 → **WebView가 앱 루트로 리로드**된다.
4. 결과적으로 결제 모듈의 `successReturnURL` 리다이렉트가 실행되지 못하고, 사용자는 홈/로그인 화면으로 튕긴다.

### 해결

`checkWebViewAndRecover()`에 **외부 도메인 체크**를 추가했다. WebView가 앱 도메인이 아닌 외부 페이지에 있으면 복구 로직을 통째로 건너뛴다.

```swift
// CustomBridgeViewController.swift

func checkWebViewAndRecover() {
    guard let webView = self.webView else { return }

    // 앱 자체 페이지가 아니면 복구하지 않음 (결제 모듈, PG, 은행 인증 등 외부 페이지)
    if let currentUrl = webView.url {
        let isOnAppPage: Bool
        if currentUrl.scheme == "capacitor" {
            isOnAppPage = true
        } else if let appHost = self.bridge?.config.serverURL.host,
                  let currentHost = currentUrl.host {
            isOnAppPage = (currentHost == appHost)
        } else {
            isOnAppPage = false
        }

        if !isOnAppPage {
            print("외부 페이지(\(currentUrl.host ?? "unknown"))에서 복귀 - 복구 건너뜀")
            return  // ← 외부 결제 페이지에서는 복구 로직을 실행하지 않음
        }
    }

    // ... 기존 초기화 체크 로직 (앱 도메인일 때만 실행)
}
```

**핵심**: WebView가 외부 페이지(결제 모듈, PG 등)에 있을 때는 복구 로직을 건너뛴다. 결제 모듈이 `successReturnURL`로 정상 리다이렉트할 시간을 확보해 주는 것이다.

## Android 이슈

Android에서는 두 가지 별개의 문제가 동시에 터졌다.

### 이슈 1: "연결 프로그램" 앱 선택 다이얼로그

#### 증상

결제 완료 후 앱으로 복귀하는 과정에서 Android 시스템의 **"연결 프로그램"** 바텀시트가 떴다. 같은 앱의 빌드 두 개가 후보로 표시되고 \[한 번만\] / \[항상\] 버튼이 노출됐다.

#### 원인

`AndroidManifest.xml`에 아래와 같은 **HTTPS App Links intent-filter**가 등록되어 있었다.

```xml
<!-- 문제를 일으킨 intent-filter (제거됨) -->
<intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:scheme="https"
          android:host="app.example.com"
          android:pathPrefix="/reservations/" />
</intent-filter>
```

이 intent-filter가 있으면 Android OS가 `https://app.example.com/reservations/success/...` URL을 앱에서 열 수 있는 것으로 판단한다. `autoVerify="true"`가 있어도 App Links 검증(`assetlinks.json`)이 실패하거나, 같은 도메인을 처리할 수 있는 앱이 두 개 이상 설치되어 있으면(개발 빌드 + 운영 빌드) **앱 선택 다이얼로그**가 표시된다.

#### 해결

`AndroidManifest.xml`에서 HTTPS intent-filter를 **모두 제거**하고, 커스텀 스킴(`myapp://action`)만 남겼다.

```xml
<!-- 유지: 커스텀 스킴만 남김 -->
<intent-filter>
    <action android:name="android.intent.action.VIEW" />
    <category android:name="android.intent.category.DEFAULT" />
    <category android:name="android.intent.category.BROWSABLE" />
    <data android:host="action" android:scheme="myapp" />
</intent-filter>
```

### 이슈 2: 결제 모듈 페이지에서 멈춤 (리다이렉트 실패)

#### 증상

앱 선택 다이얼로그 문제를 해결한 뒤에는, 결제 완료 시 앱이 **결제 모듈 페이지에 그대로 멈춰** 있었다. "결과를 호출 서비스로 전달 중입니다" 단계까지는 보이지만 `successReturnURL`로의 리다이렉트가 실행되지 않았다.

흥미롭게도 앱을 완전히 종료한 뒤 재시작하면, 복구 로직(`recoverPendingPayment()`)에 의해 정상적으로 "예약 완료" 페이지가 표시됐다. 이 단서가 원인 추적의 결정적 힌트가 됐다.

#### 원인

Android WebView의 **JavaScript 실행 중단(suspend)** 문제였다.

1. 사용자가 결제 앱으로 이동하면 우리 앱의 Activity가 `onPause()` 상태로 전환된다.
2. Android OS는 백그라운드로 내려간 Activity의 WebView에서 **JavaScript 실행을 중단**시킨다.
3. 결제 모듈이 서버에서 결제 승인 결과를 받아 `window.location.href = successReturnURL`로 리다이렉트하려 하지만, **JS가 중단된 상태**라 실행되지 못한다.
4. 사용자가 결제 앱에서 돌아와 `onResume()`이 호출되어도, WebView는 여전히 결제 모듈 페이지에 머물러 있다. 결제 모듈의 JS는 이미 실행이 끝났거나, 페이지 라이프사이클이 리다이렉트를 재시도하지 않는다.
5. 결과적으로 WebView는 **결제 모듈 페이지에서 멈춰** 있고, 앱의 SPA 라우터로 돌아가지 못한다.

#### 해결

`MainActivity.java`에 **`onResume()` 복구 로직**을 추가했다. iOS의 `checkWebViewAndRecover()` 패턴을 참고했지만 **동작 방향은 정반대**다.

- **iOS**: 외부 결제 페이지면 복구를 **건너뜀** (결제 모듈이 스스로 리다이렉트하도록 기다린다)
- **Android**: 외부 결제 페이지면 **앱 URL로 강제 이동** (JS가 중단돼 리다이렉트가 불가능하므로 우리가 대신 밀어준다)

```java
// MainActivity.java

private boolean wasInBackground = false;

@Override
public void onPause() {
    super.onPause();
    wasInBackground = true;
}

@Override
public void onResume() {
    super.onResume();
    setSafeAreaInsets();

    if (wasInBackground) {
        wasInBackground = false;
        recoverFromPaymentIfNeeded();
    }
}

private void recoverFromPaymentIfNeeded() {
    String currentUrl = bridge.getWebView().getUrl();
    if (currentUrl == null) return;

    boolean isOnPaymentDomain =
        currentUrl.contains("pay.example.com") ||      // 자체 결제 모듈
        currentUrl.contains("pg-provider-a.com") ||    // 외부 PG A
        currentUrl.contains("pg-provider-b.com");      // 외부 PG B

    if (isOnPaymentDomain) {
        Log.d("MainActivity", "결제 도메인에서 복귀 감지, 앱 URL로 이동: " + currentUrl);
        bridge.getWebView().post(() -> {
            String appUrl = bridge.getConfig().getServerUrl();
            if (appUrl != null) {
                bridge.getWebView().loadUrl(appUrl);
            }
        });
    }
}
```

#### 복구 흐름

```
외부 결제 앱 → 앱 복귀 (onResume)
→ recoverFromPaymentIfNeeded() 실행
→ WebView URL이 결제 도메인인지 확인
→ 결제 도메인이면 앱 URL(serverUrl)로 WebView를 강제 이동
→ 앱 루트('/') 로드 → IndexPage 마운트
→ recoverPendingPayment() 실행 (localStorage의 pendingReservationId 확인)
→ 서버에서 예약 상태 폴링 (pollReservationStatus)
→ CONFIRMED → /reservation/complete/{id}/ (예약 완료 페이지)
→ FAILED   → 실패 다이얼로그 + /reservation/confirm/
→ TIMEOUT  → /reservation/history/{id}/ (이용 내역)
```

## 프론트엔드 보조 처리

### 정적 성공/실패 페이지

결제 모듈의 `successReturnURL` / `failReturnURL`은 정적 HTML 페이지로 설정되어 있다.

- `src/public/reservations/success/index.html`
- `src/public/reservations/fail/index.html`

이 페이지들은 WebView 환경인지(전용 User-Agent로 감지) 외부 브라우저인지 판별해서 분기한다.

- **WebView**: `window.location.replace()`로 SPA 라우트로 즉시 이동
- **외부 브라우저**: 커스텀 스킴(`myapp://`)으로 앱 열기 시도, 실패 시 1.5초 후 웹 폴백

### pendingReservationId 복구 (IndexPage)

`src/pages/IndexPage.tsx`의 `recoverPendingPayment()`는 앱이 루트('/')로 진입할 때마다 실행된다. `localStorage`에 `pendingReservationId`가 남아 있으면 서버에서 예약 상태를 확인하고 적절한 페이지로 분기한다. Android의 `recoverFromPaymentIfNeeded()`가 앱 URL로 강제 이동시키면 바로 이 복구 로직이 트리거된다.

### Deep Link 리스너 (App.tsx)

`setupDeepLinkListener()`가 커스텀 스킴과 HTTPS App Links를 처리한다. 결제 성공/실패 타입에 따라 적절한 페이지로 라우팅한다.

## iOS vs Android 비교

| 항목 | iOS | Android |
|---|---|---|
| **핵심 문제** | WebView 복구 로직이 결제 페이지를 비정상 상태로 오판하여 리로드 | WebView JS가 백그라운드에서 중단되어 리다이렉트 실패 |
| **해결 방향** | 외부 결제 페이지면 복구를 **건너뜀** | 외부 결제 페이지면 앱 URL로 **강제 이동** |
| **수정 파일** | `CustomBridgeViewController.swift` | `MainActivity.java`, `AndroidManifest.xml` |
| **복구 트리거** | 결제 모듈이 자체적으로 `successReturnURL` 리다이렉트 수행 | `onResume()` → 앱 URL 이동 → `recoverPendingPayment()` |
| **JS가 중단되지 않는 이유** | WKWebView는 백그라운드에서 JS 실행을 즉시 중단하지 않아, 결제 모듈의 리다이렉트가 완료될 시간이 있음 | Android WebView는 Activity `onPause()` 시점에 JS를 바로 suspend |

## 수정 파일 목록

| 파일 | 변경 내용 |
|---|---|
| `CustomBridgeViewController.swift` (iOS) | `checkWebViewAndRecover()`에 외부 도메인 체크 추가 — 앱 도메인이 아니면 복구 건너뜀 |
| `MainActivity.java` (Android) | `wasInBackground` 플래그, `onPause()`, `onResume()`, `recoverFromPaymentIfNeeded()` 추가 |
| `AndroidManifest.xml` (Android) | HTTPS `autoVerify` intent-filter 제거 (커스텀 스킴만 유지) |
| `reservations/success/index.html` | 외부 브라우저 vs WebView 분기, 커스텀 스킴 폴백 추가 |
| `reservations/fail/index.html` | 동일 패턴 적용 |
| `App.tsx` | `setupDeepLinkListener()` 추가 (커스텀 스킴 + HTTPS deep link 처리) |

## 회고하며 — 주의사항과 배운 점

- **결제 도메인 목록은 하드코딩의 덫**: `recoverFromPaymentIfNeeded()`에 결제 도메인이 하드코딩되어 있다. 새로운 PG나 결제 모듈이 추가되면 반드시 업데이트해야 한다. 설정/원격 구성으로 빼는 것을 다음 개선 과제로 남겨 둔다.
- **`pendingReservationId`는 생명줄**: 결제 시작 시 반드시 `localStorage`에 저장해 둬야 Android 복구 흐름이 동작한다. 저장 누락이 곧 복구 불가로 이어진다.
- **개발/운영 빌드 동시 설치 주의**: 같은 기기에 두 빌드가 깔려 있으면 커스텀 스킴이 충돌할 수 있다. 테스트 시 한쪽만 설치하는 것을 권장한다.
- **가장 큰 교훈**: "같은 증상"이라고 해서 "같은 원인"은 아니다. iOS와 Android는 WebView 라이프사이클 처리 방식 자체가 달랐고, 그래서 해결책도 정반대(기다리기 vs 밀어주기)가 됐다. 플랫폼별 동작 모델을 이해하는 것이 결국 가장 빠른 길이었다.
