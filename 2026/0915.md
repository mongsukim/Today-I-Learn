
# 클로드와의 대화
## 1. 건물 빌딩 관리 시스템 하이브리드 앱

Q. 이 프로젝트에서 내가 프론트엔드개발자로써 쌓을 수 있는 역량은 뭘까 ?

```
A. 코드베이스를 직접 훑어봤어요. 소스 973개, 컴포넌트 429개, 페이지 301개 규모에
커밋 기여도 2위(704+550)면 이미 이 프로젝트의 주요 오너 중 한 명이네요. 정리하면 이렇습니다.
```


### 이미 쌓이고 있는 것 (이력서에 쓸 수 있는 것)


#### 1. 레거시 점진 마이그레이션 설계 — 가장 값어치 있는 경험  
v1 컴포넌트를 건드리지 않고 ds/에 v2를 별도로 쌓아 페이지 단위로 교체하고, REACT_APP_UI_RENEWAL_* 피처플래그로 스위칭하는 구조. 이건 교과서적인 Strangler Fig 패턴이고, "왜 빅뱅 리라이트 대신 이 방식을 택했고 어떤 트레이드오프를 감수했나"를 설명할 수 있으면 경력 5~10년차 면접에서 바로 먹히는 소재예요.

#### 2. 디자인 시스템 구축  
atoms 36 / molecules 46 / organisms 16, CVA + tailwind-merge + 토큰 체계, .theme-v2 클래스로 v1/v2 팔레트 런타임 전환. 게다가 tailwind-merge가 text-body1-m과 text-gray-900을 같은 유틸리티로 먹어버리는 함정까지 문서화해둔 걸 보면 — 이건 "컴포넌트 좀 만들어봤다"가 아니라 시스템 레벨 이해예요.

#### 3. 네이티브 웹뷰 브릿지 — 이 프로젝트에서만 얻는 희소 역량
useBLEAdvertising, useBLEScanning, useNfc, useQrScanner, useBioMetrics, useGPS, usePush, useKeyboardHeight/Overlap, useNativeBackHome, historyStack. 순수 웹 개발자는 평생 못 만져보는 영역이고, 최근 커밋(iOS 키보드 여백, 히스토리 스택 바닥 보정, 뒤로가기 스크롤 복원)이 전부 여기예요. "웹뷰 안의 웹은 웹이 아니다"를 몸으로 아는 사람은 시장에 드뭅니다.

#### 4. 테스트 문화
Jest + RTL 테스트 129개, 공통 render wrapper, 룰 기반 테스트(reservationSpaceCard.rules.test.ts). 프론트에서 테스트를 실제로 굴려본 경험은 생각보다 희소해요.


### 지금 비어 있는 것 = 성장 기회

#### ① 번들 최적화 — 가장 임팩트 큰 빈칸

build/assets/index-*.js  →  4.7 MB (단일 번들)
routes.tsx 내 React.lazy  →  0개
빌드 타깃  →  chrome70 / Android 7.1 웹뷰

Android 7.1 저사양 기기에서 4.7MB 단일 번들을 파싱하고 있어요. 라우트 단위 lazy() + manualChunks로 쪼개면 초기 진입 체감이 눈에 띄게 달라집니다. web-vitals가 이미 설치돼 있으니 LCP/INP를 GA로 흘려서 "개선 전/후 숫자"를 만드는 것까지 가면 — 정량 성과가 있는 성능 최적화 경험이 됩니다. 이게 이 프로젝트에서 뽑아낼 수 있는 가장 좋은 한 줄이에요.

#### ② 서버 상태 아키텍처 통일
React Query를 쓰는 파일 25개 vs useEffect가 있는 페이지 파일 216개. 전환이 초반이라는 뜻이고, 거꾸로 말하면 마이그레이션 전략을 직접 설계할 자리가 비어 있다는 뜻입니다. queryKeys.ts 팩토리와 LIST_STALE_TIME 규칙을 이미 잡아놨으니 뼈대는 있어요.

#### ③ 접근성
aria-* 232개는 나쁘지 않은데 <div onClick> 29개가 남아 있어요. 공공/기업 빌딩 관리 앱이면 접근성 요구가 들어올 가능성이 높고, 미리 해두면 방어 논리가 생깁니다.

#### ④ 없는 것들
Storybook 없음(ds/ 100+ 컴포넌트가 있는데 카탈로그가 없어요),
E2E 없음, 
CI는 deploy.yml 하나뿐 — 테스트/타입체크 게이트가 파이프라인에 없습니다. 
셋 중 하나만 도입해도 "프론트 인프라 만든 사람"이 됩니다.


### 만약 우선순위를 하나 고른다면

번들 스플리팅 + Web Vitals 계측을 추천해요.   
이유는 세 가지: 혼자 끝낼 수 있고, 숫자로 증명되고, 디자인 시스템이나 마이그레이션과 달리 "내가 주도했다"가 명확한 단위 작업이라서요.  
SA2025 티켓 하나 끊어서 전/후 리포트까지 남겨두면 평가 시즌에 그대로 씁니다.  

혹시 현재 라우트 구조 기준으로 코드 스플리팅을 어디부터 쪼개는 게 효율적인지 분석해드릴까요? routes.tsx 1580줄을 기준으로 청크 경계를 잡아볼 수 있어요.

## 2. 통근버스 앱 

코드베이스를 봤어요. 결론부터: 이 프로젝트가 SANDI보다 역량 레버리지가 훨씬 큽니다. 커밋 1065개로 전체의 약 62%, 사실상 이 앱의 메인 오너예요.  

이 프로젝트의 성격이 다릅니다  

SANDI는 "네이티브 앱 안에 들어가는 웹"이었다면, 여기는 앱 자체를 프론트엔드가 만듭니다.  

```
Capacitor 7 + Framework7 8 + React 19 + Vite 7 + TS 5.9
Tailwind 4 / zustand / React Query 5 / Sentry / TossPayments
android/ ios/ 네이티브 프로젝트를 직접 관리
```

그리고 단일 앱이 아니라 생태계예요 — 
bus-frontend(앱), bus-bo-frontend(관리자, antd+tiptap), core-idv-frontend(본인인증), 
core-payment-frontend(토스페이먼츠), bus-contracts(API 계약 레포). 
본인인증·결제를 별도 프론트엔드로 떼어낸 구조는 사실상 마이크로 프론트엔드 설계고, 
이건 이력서에서 "화면 만들었다"와 완전히 다른 층위의 이야기입니다.


### 이미 쌓인 것 중 가장 값진 것

#### 1. 하이브리드 앱 함정 백과사전 — CLAUDE.md 2,192줄

이건 제가 본 것 중 가장 밀도 높은 하이브리드 앱 문서예요. 목차만 봐도:

외부 결제 앱 복귀 시 WebView 복구 — iOS는 건너뛰고 Android는 앱 URL로 강제 이동, 그 차이의 이유까지
router.back() popstate 이중 실행
Android HTTPS intent-filter 사용 금지 (앱 선택 다이얼로그 문제)
cap sync 없이 빌드하면 예전 설정이 조용히 실려나가는 사고 (BUS-2631)
iOS WebKit button 내부 flex 자식 너비 문제
페이지 이동 중 API abort → UnhandledRejection (Sentry SANDIBUS-PRD-5)

이건 문서가 아니라 자산입니다. "장애를 겪고 → 원인을 규명하고 → 재발 방지 규칙으로 고정했다"의 증거가 수십 건 쌓여 있어요. 면접에서 이 중 두세 개만 풀어내도 시니어 판정이 납니다.

#### 2. 빌드 파이프라인 설계 — vite.config.ts

특히 이 부분이 눈에 띄었어요:

Tailwind v4의 네이티브 CSS 중첩을 구형 WebView(Chrome 101)가 통째로 버려서 arbitrary variant 47개가 죽었다 → css.transformer: 'lightningcss'로 dev·build 양쪽을 일치시킴

"개발 서버에서만 멀쩡하고 실기기에서만 깨지는" 문제를 툴체인 레벨에서 구조적으로 막은 것 — 이게 프론트엔드 인프라 역량이에요. 오프라인 error.html을 빌드타임에 같은 소스로 치환하는 커스텀 Vite 플러그인, Sentry 소스맵 업로드 + release 버전 연동도 같은 결입니다.

#### 3. 규제 도메인 — 결제 + 본인인증

TossPayments, 카드사 앱 딥링크와 미설치 시 스토어 폴백, Mobile-OK 본인인증,   
중복 제출 방지, 결제 완료 후 뒤로가기 차단, 진행 중 이탈 방지.   
돈이 오가는 화면의 엣지 케이스를 아는 프론트엔드는 채용 시장에서 확실한 프리미엄이 붙어요.  

#### 4. QA 방법론

QA-더보기-시나리오.md(43KB),
QA-회원가입-로그인-약관재동의.md(39KB), 
.qa-reports/ 자동 리포트, 피그마 비교 검증 문서. 
개발자가 QA 시나리오를 문서로 설계하는 건 흔치 않습니다.


###### 먼저 손봐야 할 것 하나

⚠️ .env.production이 git에 추적되고 있고, 거기 VITE_SENTRY_AUTH_TOKEN에 값이 들어 있어요.

.mcp.json은 gitignore 처리돼 있는데 .env.production은 아니라서 Sentry auth 토큰이 히스토리에 남아 있습니다. 
이 토큰은 릴리즈 업로드·삭제, 프로젝트 조회 권한이 있어요. 토큰 폐기 후 재발급 → CI 시크릿이나 로컬 .env.local로 이동을 권합니다.
히스토리에서 지우는 건 공유 레포라 리스크가 있으니 폐기·교체가 우선이에요.

##### 나머지 성장 기회

① 라우트 코드 스플리팅 (SANDI와 동일한 빈칸)

src/routes/index.ts (450줄)  →  동적 import 0개
dist/assets/main-*.js        →  2.07 MB

framework7, react는 manualChunks로 분리해놨는데 정작 앱 코드 2MB가 통짜예요. 결제·본인인증·QR 같은 무거운 흐름부터 lazy()로 떼면 초기 진입이 개선됩니다. rollup-plugin-visualizer가 이미 붙어 있어서 stats.html로 전후 비교가 바로 나와요 — 측정 도구가 이미 있는데 안 쓰고 있는 상태라 착수 비용이 거의 없습니다.

② CI 파이프라인 부재

.github/에 워크플로가 없고 커밋 지침 md만 있어요. 게이트는 pre-commit prettier 검사 하나뿐입니다. check-all 스크립트(type-check + lint + format:check)가 이미 정의돼 있으니 GitHub Actions에 그대로 태우는 것만으로 하루 작업이고, 여기에 jest 추가하면 테스트 61개가 비로소 안전망이 됩니다. coverage 리포트도 생성은 되는데 아무도 안 보고 있어요.

③ 접근성 — SANDI보다 오히려 약합니다

aria-* 38곳(SANDI는 232곳). 대중교통 서비스라 접근성 요구가 들어올 가능성이 SANDI보다 높습니다.

두 프로젝트를 이렇게 나눠 쓰세요
	SANDI	샌디버스
역할	팀원 (커밋 2위)	오너 (커밋 62%)
서사	레거시 마이그레이션 · 디자인 시스템	앱 아키텍처 · 결제 · 빌드 인프라
희소성	웹뷰 대응	Capacitor 네이티브 빌드 · 규제 도메인

SANDI는 "대규모 레거시를 무중단으로 개선한 경험"으로, 샌디버스는 **"앱 하나를 아키텍처부터 배포 파이프라인까지 책임진 경험"**으로 쓰는 게 맞습니다. 후자가 훨씬 강한 카드예요.

한 가지만 고른다면 — CI 파이프라인 구축을 추천합니다. 코드 스플리팅보다 우선인 이유는, 62% 오너십을 가진 사람이 만든 규칙(CLAUDE.md 2,192줄)이 지금 강제력 없이 문서로만 존재하기 때문이에요. CI는 그 규칙을 조직의 자산으로 바꿔줍니다. 그다음이 스플리팅이고요.
